## Notes

- Phases 2A, 2B, and 2C may run in parallel only after Phase 1 contracts are fixed; they must remain dormant and must not alter active runtime startup, schema migration, protocol v2, CLI behavior, or package exports.
- Phase 3 may connect dormant components only through an internal activation seam. It must not expose a supported SDK or reset a normal state root.
- Phase 4 is the sole coordinated activation boundary: Tasks 4.1–4.7 prepare complete but unselected candidate paths, and Task 4.8 is the only task permitted to select the new schema, runtime, Pi ingestion, service, protocol, socket client, CLI, receive, UUID, continuity, destruction, and shutdown behavior while removing the old selected path.
- Phase 5A and Phase 5B may run in parallel after Phase 4; shared client/build/package files remain serialized through Phase 6.
- State-root hardening and old-runtime/process ownership gates precede destructive activation because no-compatibility policy does not relax single-writer or sensitive-data safety.
- Exact numeric queue, batch, page, checkpoint, timeout, and resource thresholds must be selected from `testing.md` evidence rather than invented in implementation tasks.
- No release, tag, npm publication, host service replacement, or migration of the user's persistent runtime occurs during implementation apply.
